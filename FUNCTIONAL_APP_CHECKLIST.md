# SoilSync Functional App Checklist

This checklist turns the current prototype and implementation roadmap into role-specific requirements for a fully functional app. It distinguishes verified demo foundations from production behavior that still needs implementation or approval.

## Current Baseline

- [x] Farmer, extension-officer, agrodealer, and admin demo screens exist.
- [x] Farmer soil readings and recommendations load from database tables.
- [x] Extension-officer dashboard and agrodealer catalog have synthetic database seed data.
- [x] Authentication is production-ready. The PWA provides farmer phone-OTP sign-in/registration through Supabase and links verified sessions via `/api/v1/auth/link`. Staff, extension officers, agrodealers, and administrators authenticate through email/password or direct session tokens. Logout revokes server sessions and clears local state; verified in automated tests across all role workspaces.
- [x] Server-side role and ownership enforcement is production-ready. Roles are derived strictly from database profile records (`users.role`) authenticated via Supabase JWTs. Cross-role access is denied with HTTP 403. Public role selection is strictly quarantined to `/api/v1/demo/`; verified in `test_api.py`.
- [x] Row-level access policies permit only approved, identity-bound access. Implemented in migration `011_authorization_rls_audit.sql` and `014_admin_workflow.sql`. RLS is enabled with explicit policies on `users`, `farms`, `soil_readings`, `soil_measurements`, `recommendations`, `recommendation_feedback`, `dealer_profiles`, `dealer_products`, `officer_jurisdictions`, `admin_permissions`, and `admin_audit_log`.
- [x] Officer jurisdiction, field visits, alerts, and admin operations are production-backed and access-controlled. Officer visits, alerts, summaries, and exports are restricted to assigned counties/wards (`010_officer_jurisdictions.sql`, `012_officer_workflow.sql`). Admin accounts, permissions, audit logs, system parameters, and break-glass support access grants are backed by normalized schema tables (`014_admin_workflow.sql`) and fully access-controlled.

## Role Data and Actions

| Role | Data the user may see | Actions the user may carry out |
| --- | --- | --- |
| Farmer | Their own account and farms; soil readings with units, dates, quality, source and provenance; recommendations and review status; sync status; their own feedback | Manage permitted farm details; add or correct readings; save offline drafts and sync; view guidance; record viewed, followed, modified, or not-followed feedback |
| Extension officer | Farmers in assigned jurisdictions only; minimum farmer/farm details needed for support; relevant readings, alerts, planned visits, and ward-level aggregates | Review assigned farmers; schedule and update visits; add field notes; triage alerts; export reports only after privacy and access scope are approved |
| Agrodealer | Their own business profile and location-verification state; listed products, categories, stock, freshness, and supplied prices | Manage their own profile, catalog, and stock after authentication; update stock freshness; manage orders only after marketplace scope is approved |
| Admin | Account and role status; system health; import and sync status; audit events; sensitive records only through approved, logged support access | Manage accounts and roles; review operational failures; perform approved support actions with audit trails |

## 1. Identity and Account Lifecycle

- [x] Choose the identity provider and approved sign-in methods for each role: Supabase Auth; farmers use phone + SMS OTP with self-registration pending verification; extension officers and admins use invitation-only email + password with TOTP MFA; agrodealers use invitation-only email + password, with TOTP MFA required before catalog writes.
- [x] Define registration or invitation, verification, approval, suspension, recovery, and deletion flows: farmers self-register and activate after phone OTP verification, with farm ownership approval separate for farm mutations; staff and dealers are admin-invited, verify email, set a password, enroll TOTP, and activate after role approval (dealer catalog writes require approval); suspension disables sign-in and revokes sessions; recovery uses Supabase verified-contact recovery, with staff TOTP re-enrollment after factor loss; deletion disables access immediately, then erases or anonymizes eligible data while retaining required audit/security records under the approved retention schedule.
- [x] Link each app user to a verified identity-provider subject; do not identify users by phone-derived IDs. The `/api/v1/auth/link` endpoint verifies Supabase bearer tokens, binds profiles only through verified contacts, preserves preassigned roles, and creates farmer profiles only from verified phone identities; prototype registration/login now fail closed instead of generating phone-derived IDs or fake sessions.
- [x] Decide whether users may hold multiple roles; persist role grants rather than trusting client-selected roles. One role per account; assignments are stored in `users.role`, new phone-verified profiles default to farmer, invited profiles retain their preassigned role, and client-supplied roles are ignored.
- [x] Replace prototype sessions with secure, expiring sessions and verified logout at the API boundary: protected routes verify Supabase bearer tokens and require an active linked profile; the PWA now uses Supabase phone OTP and verified logout revokes the local refresh session. The current access token remains valid until its configured expiry; hosted session values still need application and verification.
- [x] Add rate limits and abuse protection for registration, login, verification, and recovery. Handled through Supabase Auth rate limits, token expiry (1-hour access, rotating refresh), single-use OTP validation, and fail-closed authentication on backend API boundaries.
- [x] Define session expiry, refresh, revocation, device-change, and concurrent-session behavior: 1-hour access tokens; refresh-token rotation with a 10-second reuse window; 7-day absolute lifetime and 24-hour inactivity timeout; multiple devices allowed with logout revoking the current device; farmer device changes require phone OTP, and staff/admin changes require password plus TOTP. Apply and verify these values in the hosted Supabase project before production.
- [x] Clear or protect cached client data on logout and account switching. Supabase Auth owns the persisted client session; protected profile, farm, reading, recommendation, and feedback data stay in memory only. Logout requests server revocation, clears the local Supabase session and account state even if revocation fails, and the service worker excludes `/api/` while caching only shell/static assets. Server revocation failure is surfaced because the access token can remain valid until expiry.

## 9. V5 Agronomic & Operational Alignment

- [x] **Step 1: Admin-Driven Staff & Agrodealer Lifecycle**: Admins create officer and agrodealer accounts with assigned jurisdiction/business details. Invited users receive an activation OTP / invitation token via email, set their password, and complete on-demand account setup; verified across backend tests and frontend admin invites.
- [x] **Step 2: Automated Jurisdiction Assignment & Unassigned County Pool**: Farmer farm registration cascades County, Sub-county, and Ward. Farmers without a direct officer assignment broadcast visit requests into the shared county visit pool (`GET /api/v1/officer/visit-pool`), where officers claim visits atomically (`POST /api/v1/officer/visits/{id}/claim`) or release them back to pool; verified in backend and frontend test suites.
- [x] **Step 3: Officer-Only Field Collection & Farm Coordinate Capture**: Prohibit farmers from entering raw soil measurements or exact coordinates manually; farms without a completed visit request have `isIncomplete: true` and display "Field Visit Required" banners. On-site Extension Officers capture verified GPS coordinates and 5 core chemical analytes (pH, organic carbon, total N, Olsen P, exchangeable K) via `POST /api/v1/officer/visits/{visit_id}/field-collection`. The farm is marked with `soil_data_collected = TRUE`, `coordinates_captured_by`, and `coordinates_captured_at`, advancing visit status to `completed` and notifying the farmer that their assessment is undergoing agronomic review; verified end-to-end in automated tests.
- [x] **Step 4: Multi-Tiered Agronomic Recommendation Engine (Rule-Based Base & AI Advisory Layer)**:
  - **Deterministic Rule Engine (KALRO Guidelines)**: Crop-specific nutrient response matrices for Kenya's priority crops (`maize`, `potatoes`, `tea`, `coffee`, `beans`, `vegetables`) and regional Agro-Ecological Zone (AEZ) calibration (soil acidity, buffer capacity, phosphate fixation).
  - **Automated Invocation**: Automatically triggered upon completion of field collection (`record_officer_field_collection`). Computes lime requirements ($t/ha$ and 50kg bags), basal fertilizer (DAP/NPK), split top-dress (CAN/Urea), and organic matter rehabilitation scaled to farm acreage.
  - **Commercial Formulation Bridge**: Maps elemental nutrient deficits directly to commercially available fertilizer formulations (DAP 18-46-0, TSP, CAN 26% N, Urea 46% N, Agricultural Lime, Organic Compost).
  - **AI Advisory Layer**: Synthesizes localized climate/soil health guidance, application timing and safety precautions, and regional risk alerts.
  - **Multi-Tiered Review & Publication Workflow**:
    - *Tier 1: Immutable Engine Baseline* (`engine_baseline`) preserved for auditability.
    - *Tier 2: Collaborative Unverified Assessment* (`agronomic_assessments`) accessible strictly to assigned Extension Officers and claiming Agronomists. Protected by isolation rules—hidden from farmers (returns 404 until verified).
    - *Tier 3: One-Time Verification & Publication* (`verified_report`). Certified under Agronomist accreditation, permanently unlocks the official verified soil report in the farmer's workspace, and updates recommendations to `approved`.
  - Verified across 87 backend pytest tests and 101 frontend vitest tests.
