# Recommendation data-flow discovery

**Scope:** WP0 of `SOILSYNC_REMEDIATION_PLAN.md`. This is a source-code discovery note only; no provider, database, engine, or workflow behavior was changed for WP0.

**Rights and deletion status:** Rights for the former project soil dataset remain unconfirmed. The local `soil_data_all.csv` copy was removed in the earlier retirement step, and demo recommendation benchmarks no longer load it. Migration `032_retire_project_soil_dataset.sql` is prepared but has not been applied to a production database. Production data removal and any retained backups/deployment copies therefore remain unverified.

## Current assessment call path

1. The extension officer opens an active, claimed visit and records field data in `ExtensionOfficerAccount.tsx`. The form clears its example state when opened. Soil pH is required; organic carbon, total nitrogen, Olsen phosphorus, and exchangeable potassium may be left blank. The current entry units are pH, `%`, `mg/kg`, and `cmol/kg`, respectively. Values are entered by the officer; the form does not identify or validate a lab, kit, or instrument.
2. The form requires location consent and a short consent note before capture/save. It sends coordinates, uncertainty, depth, measurements, notes, sampled time, and `mark_completed`. It does **not** send the consent checkbox or note. The officer request model has no consent fields, and the field-collection persistence path does not store that consent. The form's consent requirement is therefore a UI-only record today.
3. `record_officer_field_collection` looks up the farm, visit, officer, and crop/geography/acreage context. If context is absent, the current path defaults county to Nyeri, acreage to 1 acre, and crop to maize; when multiple crops are listed, it uses the first comma-separated crop. Depth defaults to 0–20 cm. The database path stores the submitted measurements as valid and defaults the analytical method to `"Field Kit / Sensor"` when one is not supplied. The UI has no method selector, so this label is not evidence of which instrument or method was actually used.
4. The database function calls `generate_agronomic_assessment` with measurement values and crop, county, subcounty, ward, acreage, and field notes. The engine is deterministic/rule-based; it does not train on the former CSV. The result is saved as an unverified assessment together with a baseline and recommendation rows in the same transaction. The separate farmer soil-reading API persists farmer-entered readings but is not the officer assessment call path.
5. Agronomists claim, edit, and publish the assessment. Assessment JSON stores `engine_baseline`, `officer_edits`, and `agronomist_edits` (migration 027). Publishing builds diagnoses and prescriptions from the baseline and applies agronomist adjustments; officer edit records are returned but are not applied to those arrays in the inspected publish function. The farmer-facing verified report displays the published diagnoses, prescriptions, inputs, schedule, certification, and notes; its current TypeScript shape does not include the raw measurements, measurement method, consent record, or provider provenance.
6. Migration 007's `recommendation_feedback` records `viewed`, `followed`, `modified`, or `not-followed`. This is interaction feedback, not measured treatment efficacy, yield, or harvest outcome.

## Measurement and workflow contracts

- The API requires at least one measurement. The officer form's required pH field is what normally satisfies this; other analytes can be absent. The engine receives parsed numeric values, not the raw instrument result, quality class, or an independently validated method.
- The principal backend contracts are in `backend/app/models.py`; the officer request and unverified-assessment TypeScript mirror are in `frontend/src/api/officer.ts`. Farmer report fields are in `frontend/src/api/farmer.ts`. These are separate definitions rather than a generated shared contract.
- Backend provider types include `OFFICER_FIELD_COLLECTION`; the frontend `SoilDataProvider` union in `frontend/src/types/soil.ts` does not. Confirm the intended shared provider vocabulary before adding provider values.
- Assessment storage permits `flagged`, and frontend types represent that status. A dedicated officer flag action/endpoint was not found in the focused workflow scan; confirm whether “flag” is intended to be a real transition or only a reserved status.
- Migration 001 has flattened soil-property columns on `soil_readings`; migration 002 adds the normalized measurement/source structure; migration 004 adds demo dashboard records; migration 007 adds farmer recommendation feedback. Dealer-location consent is handled separately for agrodealer profiles in migration 013; it does not persist consent for officer field collection.

## Open questions before subsequent work packages

1. **Operations / measurement provenance:** What instruments, kits, or accredited labs do officers actually use; who supplies them; and how are calibration, units, detection limits, sampling depth, and method recorded? The current `"Field Kit / Sensor"` fallback is generic and may be inaccurate.
2. **Consent and location purpose:** What exact consent text, scope, retention, and sharing purpose are required? Should consent be persisted with the visit/reading, and what should happen when it is declined? Current UI state is not persisted.
3. **Assessment context quality:** Should crop, county, and acreage be mandatory rather than silently defaulted? How should multiple crops be represented and assessed?
4. **Feedback/outcomes:** What measured post-treatment observations (including dates, rates actually applied, yields, and units) can be collected lawfully and reliably? Migration 007 feedback does not answer this.
5. **Review workflow:** Is a formal officer “flag” action required? Should officer adjustments affect the final published report, or should only agronomist adjustments do so?
6. **Provider and product policy:** What source license/terms, attribution, depth compatibility, spatial resolution, uncertainty, and farmer-facing disclosure are required before any iSDA/ISRIC estimate can be used? No provider was activated as part of WP0.
7. **Legacy retirement verification:** Which production database, backups, exports, analytics stores, and deployed artifacts must be audited after applying migration 032? The configured production target and deletion evidence remain unavailable.
